# ADR 003 本地持久化方案：版本化原子快照

- 状态：**已采纳（2026-09-23）**
- 日期：2026-09-23
- 关联任务：TASK-06（实现）、TASK-03（候选记录）、ADR-002 §1（存储候选）
- 决策范围：持久化技术选型、数据目录、一致性边界、单写者锁、刷盘与原子替换语义、摘要算法、迁移策略

## 1. 决策

正式持久化方案为**版本化原子 JSON 快照**，**不采用 SQLite**。

一个存档 = 一个自包含信封文件，内含**完整机械状态**（`GameState`）、随机流、未决子状态、幂等账本与日志尾。写入路径为：同目录临时文件 → 写入 → 刷盘（file）→ 原子替换 → 刷盘（目录）。**不存在拆成若干互不原子写入的情况**，因为一致性单元就是这一个文件。

之所以能用一个文件承载全部一致状态，是 TASK-05 的直接结果：`interactionSeq`、`worldMonth`、`combatRound` 与四个随机流都已经是 `GameState` 的**值字段**，幂等账本与未决候选也都在信封里。SQLite 的多表事务在此解决的是一个**本方案不存在的问题**：我们没有被拆散的一致性单元需要跨表绑定。

数据根目录为 `%LOCALAPPDATA%\WendaoChangsheng\`。**不写入安装目录，不写入当前工作目录或仓库。**解析顺序实现为：显式覆盖（测试与便携用途）→ `%LOCALAPPDATA%` → 明确报错。**没有"回退到当前目录"这一分支**，因为那正是设计文档禁止的行为。

每个存档**单写者**：进程持有独占锁，第二个进程要么只读、要么明确拒绝。崩溃残留锁有安全恢复流程，**不删锁覆盖活跃进程**。

跨版本迁移采用**显式映射表**；无法保真迁移时**拒绝载入并保留原档**，提示用原版本继续。**绝不静默清空战斗或重新抽奖。**

## 2. 为什么不是 SQLite

ADR-002 把 SQLite 保留为回退方案。经实现层面对照，回退条件**未触发**，理由如下：

| 维度 | 版本化原子快照 | SQLite | 本项目的取值 |
| --- | --- | --- | --- |
| 一致性单元 | 单文件，天然原子 | 需显式事务包裹多表写 | 快照胜（单元本就只有一个） |
| 第三方依赖 | **零** | 需引入 Go 驱动或 CGO（违反 ADR-002 的 `CGO_ENABLED=0`） | 快照胜（硬约束） |
| 崩溃后状态 | 旧完整 或 新完整，二值 | 旧完整 或 新完整，二值（WAL 下可能带热日志） | 平手 |
| 可检查性 | 文本 JSON，玩家可直接读、可手改、可 diff | 二进制，需工具 | 快照胜（设计文档要求"可导出检查"） |
| 存档规模 | 单角色，量级 KB～百 KB | 为更大数据设计 | 快照足够 |
| 查询需求 | 无（不需要按字段检索存档） | 有优势 | 快照足够 |
| 实现与审计成本 | 低，约数百行可读 | 高，需理解 WAL/刷盘/锁语义 | 快照胜 |

**决定性理由是零依赖**：ADR-002 要求 `CGO_ENABLED=0` 且便携包不下载组件。纯 Go 的 SQLite 实现（modernc.org/sqlite）会是本项目**第一个第三方依赖**，而它换来的能力（跨表事务、索引查询）在本项目**没有使用者**。

**回退条件（保留记录）**：若未来出现「需要按字段检索大量历史记录」或「单存档规模增长到开一次档需要秒级」的情形，应重开本决策，而不是把快照方案改造成半吊子数据库。

## 3. 数据目录

```text
%LOCALAPPDATA%\WendaoChangsheng\
├── chars\
│   └── <gameId>\
│       ├── save.json            自动恢复点（当前）
│       ├── save.json.prev       自动恢复点（上一份有效）
│       ├── checkpoints\         高风险前检查点，保留最近 5 份
│       │   └── <revision>.json
│       └── manual\              手动命名档，不自动删除
│           └── <name>.json
├── settings.json                主题/色档/静音等，与进度分离
└── logs\                        滚动诊断日志，单文件 1MB、轮转 3 份
```

**设置与进度分离**：`settings.json` 损坏时回退安全默认，**不破坏进度**。

**目录缺失或不可写时明确报错**，错误信息须含实际尝试的路径与原因（权限、磁盘满、路径不存在分别区分），使玩家能自行处理。

## 4. 一致性、刷盘与原子替换

### 4.1 写入序列

1. 在**同一目录**创建临时文件（同目录是原子替换的前提；跨目录替换会退化为复制+删除，不具原子性）。
2. 写入完整信封字节。
3. `File.Sync()` — 把文件内容刷到持久介质。
4. `os.Rename(tmp, target)` — 原子替换。
5. **同步目录** — 使改名本身持久化。Windows 上目录同步不受支持，实现须显式记录这一平台差异，**不得假装做过**。

### 4.2 保留上一份

替换前先确保 `save.json.prev` 是当前 `save.json` 的内容。这样任意时刻至少有一份完整档可读：写入中被杀 → 得到旧完整（`prev`）或新完整（`target`）。

### 4.3 不宣称超出实测的持久性

设计文档明确警告：**不能仅以"写了临时文件"宣称断电安全**。因此：

- 本 ADR 只声明**进程被杀**（`kill -9` / `TerminateProcess`）下的恢复语义，并用故障注入**实测**。
- **不声明**断电安全：真实断电涉及存储设备缓存与文件系统日志语义，本机无法可信重放。这一点如实记录为未验证边界，不写"已证明断电安全"。
- NTFS 上 `os.Rename` 对同目录同卷文件是原子的，这是**平台事实**而非本项目保证；实现与文档均以实测行为为准。

## 5. 摘要算法

信封沿用 `IntegrityAlgorithmFP = "fnv1a64-canonical-v1"`，**不在此任务升级为加密摘要**。

### 5.1 为什么沿用

TASK-04 的信封注释已写明该摘要的用途是**检测截断与意外编辑，不是对抗有决心的对手**。FNV-1a 是 GF(2) 上线性的非加密散列，碰撞可由解线性方程组构造——**这一点是已知弱点，不是疏漏**。但本项目是单机游戏，玩家能直接编辑自己的存档文件；摘要的作用是"防止文件损坏或半截写入被当成好档"，而非防篡改。跨版本迁移另有版本号、迁移映射与完整性复核，不依赖摘要强度。

### 5.2 变更成本

摘要**输入**（`CanonicalString`）在 TASK-04 之后已被冻结：改变它的字段覆盖会让**所有既有存档的摘要失效**。ADR-003 因此**不动**它，包括 TASK-05 记录中的已知缺口（`Condition.Effects`、NPC 年龄等字段不在摘要内）。

**缺口补上的排期与前置条件**：必须与 `SchemaVersion` 提升成对发生。TASK-06 引入迁移机制后，这一变更**第一次变得可安全执行**——但在**没有任何玩家存档存在**的当前阶段，补缺口的收益为零而风险为"引入本可避免的迁移路径"。故 TASK-06 **仍不补**，由迁移机制就绪后的首个 schema 变更顺带完成。`TestCanonicalStringDoesNotCoverConditionEffects` 会拦住任何未经思考的补写。

### 5.3 存储层可加更强摘要

TASK-04 的信封注释已预留：存储层可通过**命名新算法**加强摘要，而不改动引擎契约。本任务不启用，因为当前威胁模型不需要。

## 6. 单写者锁

- 锁文件置于数据根目录，记录持有者（PID、进程启动时间、机器名）与获取时刻。
- 第二个进程尝试获取时：**若要写，明确拒绝**并提示已有进程；**只读则允许**。
- **残留锁恢复**：持有者的 PID 已不存在（或进程启动时间不匹配，防 PID 复用）时，锁为陈旧，可安全接管。**不得仅凭文件存在就删锁**——那会覆盖活跃进程。

## 7. 迁移策略

判定顺序（未来版本优先于旧版本判定，因为"更高版本"必然也是"非当前版本"）：

| 情形 | 处理 |
| --- | --- |
| 信封/规则/内容版本全等 | 正常载入 |
| 任一版本**高于**本程序 | **拒绝**，提示用更新的版本打开。绝不尝试解读未来格式 |
| 任一版本低于当前且有迁移映射 | 依映射升级，逐级应用 |
| 有缺失映射 | **拒绝载入并保留原档**，提示用原版本继续 |
| 完整性校验失败 | 尝试 `prev`；`prev` 也失败则报错。**不覆盖任何一份** |

**迁移必须保留**：未决事件及其冻结候选、战斗阶段、已扣材料、随机流位置。任何一步无法保真 → 整档拒绝，**不静默清空战斗、不重新抽奖**。

### 7.1 迁移在实现上分三类错误

代码里 `ErrSaveCorrupt`、`ErrSaveUnsupported`、`ErrMigrationUnavailable`、`ErrMigrationRefused` 是**四个不同的错误**，不能合并。理由不是代码整洁，而是**玩家要采取的行动不同**：

| 错误 | 玩家该做什么 |
| --- | --- |
| `ErrSaveCorrupt` | 从备份恢复；原档已保留在 `preserved/` |
| `ErrSaveUnsupported`（有更高版本号） | **升级游戏**，不要动文件 |
| `ErrMigrationUnavailable`（缺映射） | **用旧版本继续**玩，或等提供映射的新版本 |
| `ErrMigrationRefused`（有映射但无法保真） | 同上，且这是本项目的决定而非版本差 |

把 `Unsupported` 报成 `Corrupt` 会把玩家推去恢复一份本来完好的档；把 `Refused` 报成 `Unavailable` 会隐瞒"我们主动拒绝了"这一事实。实现上有一条硬规则：**两个不同类别的错误不得同时被同一个 error 匹配到**——`errors.Is` 无法区分"主因"和"顺带提到"，所以拒绝路径只挂载一个类别，另一个在**消息文本**里说明（供人阅读，不影响机器判定）。

### 7.2 迁移链必须是完整或不做

`PlanMigration` 在链中有缺口时返回**空计划**，而不是已收集到的那几步。理由：调用方若"记下错误然后照常应用返回的步骤"，就会半迁移，产出一份**声称某个版本但并不具备该版本形状**的文档——比直接拒绝更糟。降级（`from > to`）永不自动执行。

### 7.3 导入的原子性靠"不写"，不靠"小心地写"

"导入坏档不覆盖当前档"的正确实现方式不是**先仔细校验再写**，而是**校验阶段完全不碰磁盘**。`ValidateImport` 与 `ImportIntoSave` 是两个分离的调用，只有前者成功返回，调用方才提交。测试用"数据根与导入文件所在目录的前后指纹"来断言这一点，且指纹**必须包含修改时间**——原子写走的是"临时文件 + 改名"，一次写入若放回相同字节，内容指纹看不出任何变化，只有时间戳能看出。**这是本项目第三次遇到"被观测的量在正确实现与缺陷实现下相等"**（前两次见 §4 与反证 15b）。

### 7.4 导出是搬字节，不是重新解释

`ExportSave` 逐字节复制，**不重新编码**。重新编码会套用本构建的格式，并可能规范化字段，于是导出文件与玩家存档实际内容产生差异，往返不再可证无损。导出**拒绝**写入数据根内部：文件对话框会打开上次的目录，而那往往就是存档目录，这是玩家最容易犯的破坏性操作。

## 8. 后果

**正面**：零第三方依赖得以保持；存档可读、可导出、可 diff；一致性模型简单到可完整审计；崩溃语义是二值的，无中间态。

**代价**：
1. 每次提交写**整个**存档，而非增量。单角色规模下可接受；若未来存档显著增大需重新评估（见 §2 回退条件）。
2. 无字段级查询能力。当前无使用者。
3. Windows 上无法同步目录，目录项持久性弱于 POSIX。**已如实记录**。
4. `encoding/json/v2` 需要 `GOEXPERIMENT=jsonv2`（见 §9），构建脚本与文档必须携带该设置。

## 9. JSON 实现选择

采用 **`encoding/json/v2`**，理由：

- v2 的 `json.Marshal` 默认**确定性排序**，并有显式 `json.Deterministic(true)` 可写明意图。
- v2 支持 `json.RejectUnknownMembers(true)`，正好服务 §7 的"未来版本不得静默解读"——**这是选 v2 的主要理由**。
- v2 仅依赖标准库内部包，**不引入第三方依赖**。

**关于 v1 的排序**：`encoding/json/v1` 对 map key 实际也做排序，实测确认（含多字节字符，按字节序）：

```text
v1: {"0":5,"Z":1,"_":4,"a":2,"~":6,"中":3}   // 三次运行一致
```

因此**不能**以"v1 不确定"为由选 v2——那会是错误的理由。v1 的真正不足是**缺少严格的未知字段拒绝**（`DisallowUnknownFields` 存在但语义与报错粒度不如 v2 的 `RejectUnknownMembers`），以及缺少显式的确定性开关可写入代码表达意图。

> 记录一次被推翻的假设：本 ADR 初稿曾声称"`json/v1` 对嵌套 map 会转义失败"。**实测否定了这一说法**——嵌套 map、单层 map、struct 字段三者的 HTML 转义均正确（`\u003cb\u003e`）。该说法已删除，因为它是错的。教训：**归档到 ADR 的行为断言必须实测，不能凭印象写入**。

**代价**：`encoding/json/v2` 在本工具链下受 `GOEXPERIMENT=jsonv2` 构建约束保护，未设置时 `go build` 直接报 `build constraints exclude all Go files`。**这是响亮的失败，不是静默降级**，因此可接受；但 `scripts/` 下所有构建与测试入口以及文档必须带上该环境变量。

**注**：本决策只影响存储层的**序列化**。引擎的**规范串与摘要**（`CanonicalString`）不使用 JSON，是手写的显式字段列举，不受本决策影响。

## 10. 验证要求

本方案**尚未定案为"已证明安全"**，须由 TASK-06 通过以下故障注入后才能声明：

- 写入中被杀进程 → 只恢复旧完整或新完整
- 磁盘满、权限失败 → 明确报错且停止后续写入行动
- 第二进程不能并写
- 导入坏档不覆盖当前档
- 未决事件、战斗轮、候选集可还原
- 旧版未决事件/战斗遇到内容 ID 删除或规则变化 → 显式映射或拒绝并保留原档

实测结果与未覆盖边界见 `doc/TASK-06-本地事务存档与恢复验证记录.md`。
