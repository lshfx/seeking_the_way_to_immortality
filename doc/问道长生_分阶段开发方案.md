### TASK-02 验证真实终端交互与布局

- **优先级：P0｜负责人角色：终端交互｜依赖：TASK-01｜状态：进行中（三项原型修正项已修复并回归；四个终端人工实测通过，含「方向键失效」缺陷修复与真机复测；字体=新宋体、代码页=936 已记录；仅 Windows Terminal 全流程待补）**
- **目标：** 证明普通终端能承载紧凑游戏界面，而非仅生成静态文本。
- **工作：** 复用原型样式思路，建立按键输入、返回/退出、resize、高度分页、焦点和输入回显恢复的小试验；验证80×24、64×20、48×16；提供真彩/基础色/无色档。

- **验收：** 自动化已覆盖80×24、64×20、48×16布局，超小尺寸提示，长字段、组合字符、焦点、分页、四档颜色输出和控制序列过滤；当前Windows PowerShell PTY已实测选择、预览、翻页、`q`退出及输入回显恢复。**2026-09-23补：**三项原型修正项已全部修复——转义序列载荷不再泄漏进画面（旧测试曾把`名[2J字`断言为正确结果）、布局溢出改为抛出`LayoutOverflow`而非静默截断（旧断言在截断后的框上仍会通过）、`compat`成为真实的256色回退档而非冒充真彩。新增自检脚本把可自动证明的项从人工确认中分离：输入解码（含OSC载荷内嵌`q`被吞掉）、渲染不改状态、非TTY拒绝与`restore`幂等、转义与字宽，19/19通过且失败时退出码非0。采集器已在PowerShell终端（120×50）与传统conhost（120×30）各取得真实记录，均4/4 PASS、utf-8中文往返一致。**2026-09-23人工实测（PowerShell终端、conhost、VS Code终端）：交互手感、拖动缩放、中断恢复（`q`/Ctrl+C/Ctrl+D）、中文与颜色观感均通过。** **实测中发现真实缺陷：方向键在PowerShell与conhost下无效**——Windows扩展键以`\x00`/`\xe0`前缀加后缀字母两字节到达，原实现读到前缀后只单次等待0.05秒取后缀，超时即把整次按键映射为`IGNORE`，前缀已消费、后缀被丢弃，按键静默失效（已用可控时序复现：后缀延迟200ms时返回`IGNORE`）。修复：后缀最多重试6次；耗尽时返回专用标记`PREFIX_RETRY`由`handle_key`显式忽略（不再当作未知按键弹出无关提示）；补齐`INSERT`/`DELETE`/`HOME`/`END`后缀。回归验证：新增5项测试，把实现回退为旧版后4项失败，证明确能捕获该缺陷。探针测试共28项通过，自检28/28。新增`diagnose_keys.py`采集终端实际发送的原始按键字节。**修复后已在PowerShell终端与conhost真机复测确认方向键恢复正常。** **2026-09-23补（诊断工具缺陷）：**用户运行`diagnose_keys.py`采集按键原始数据，输出显示全部"未识别"。逐条比对确认**不是产品缺陷，而是诊断工具自身三处bug**：(1) `hexdump`按UTF-16低字节在前打印，真实`H`被显示成`48 00`，byte顺序看似反转；(2) `classify`与字面量`"\x00H"`比较，而`msvcrt.getwch()`把第二个键盘字节`0xE0`返回为`U+00E0`，真实终端输入永远匹配不上，只有`up`因后缀恰为`H`而看似正常；(3) `read_raw`尾部收集窗口每读一字符即重置，快速连按被合并进同一次采集，导致每行整体错位一格（用户数据中`up`行只剩前缀、`enter`行收到`M`、`tab`行多出`P`，整批数据向后错一格后`down→UP`、`left→DOWN`、`right→LEFT`、`enter→RIGHT`完美吻合）。修复后同一批原始数据全部正确解码为`前缀0xE0+后缀字母`，反证终端表示与解码器假设一致；另用打桩输入直接测试`TerminalInput.read_key`，12种扩展键组合与晚到后缀重试均正确。新增`test_diagnose_keys.py`15项测试，回退旧实现后13项失败。探针测试共**43项**通过。**已记录字体=新宋体（16磅）、控制台代码页=936（GBK）**；程序显式使用UTF-8输出，不依赖系统代码页。仅Windows Terminal全流程待补，故本任务未标通过。
- **原型修正项：** `bad`结果必须影响测试成败；字宽检查不能在内容截断后仍宣称完整；compat必须是真正的色码回退。无需维护旧HTML为产品界面。
- **阻塞：** 若中文或终端恢复不可接受，调整实现方案，不以“换字体就好”作为唯一退路。

### 13.2 Session接口

下面使用语言无关记法，实际类型由TASK-04实现。Command.kind、payload等由判别联合或等效schema约束，不能以任意对象绕过校验。

```text
query(state, queryKind) -> PanelModel
prepare(state, input, viewToken) -> Rejected | Proposal
submit(command, storage) -> CommandResult
resume(saveId) -> Session | RecoveryRequired

Proposal:
  proposalId, expectedRevision, viewToken, targetInstanceId,
  commandKind, validatedPayload, costs, timeCostMonths,
  riskText, requiresConfirmation

CommandResult:
  actionId, status, committedRevision?, phase,
  ledgerEntries[], pendingChoice?, errorCode?, panelModel
```

prepare只预览成本和风险，不抽结果骰、不扣材料；凡需要抽取可供选择的随机候选，都必须成为提交后保存的待决节点。confirmationToken绑定提案内容和revision；成本、目标、版本变化后必须重新预览。

status建议枚举为`committed / duplicate / rejected / save_failed`。只有committed和已确认落盘的duplicate可显示“已保存”。duplicate返回原结果；相同actionId而payload不一致返回`ACTION_ID_CONFLICT`。用户主动再做一次相同行为是新actionId，并接受新revision校验。

### 13.3 错误与恢复契约

| 错误码 | 是否改变领域状态 | 用户看到的下一步 |
|---|---|---|
| INVALID_ACTION / STALE_VIEW | 否 | 当前动作不可用或界面已变化；刷新当前选项 |
| INSUFFICIENT_RESOURCE | 否 | 缺少何种资源及数量，返回原场景 |
| CONFIRM_REQUIRED | 否 | 成本、风险、确认与取消 |
| SAVE_WRITE_FAILED | 无已确认提交 | 提示最后落盘版本，重试或明确退出 |
| SAVE_CORRUPT | 否 | 保留坏档，列出合法备份；不自动覆盖 |
| SAVE_VERSION_NEWER | 否 | 提示用兼容版本打开，保留原档 |
| SAVE_LOCKED | 否 | 指出该角色已被另一进程使用，退出或选择其他角色 |
| CONTENT_REFERENCE_MISSING | 否 | 显示缺少内容版本，提供恢复原包建议 |

SAVE_WRITE_FAILED中如果底层无法确认替换或事务是否完成，必须先重新读取权威存储再决定恢复旧版本或返回已提交结果；不能盲重试生成新actionId。候选随机状态保留，成功前不再执行下一行动。

### 13.4 内容包最小校验

manifest至少保存`contentVersion`、兼容规则版本、开放境界和文件校验信息。每个事件使用稳定定义ID，运行实例另有ID；委托奖励按实例去重，定义可重复不等于同一实例可重复领奖。

配置校验必须拒绝：重复ID、缺后继节点、无效物品引用、负成本、概率越界、空选择集、宣告可重复却没有时间或实例门槛的资源奖励。条件范围分析不能替代实际路径测试；两条早期目标和筑基所需资源必须有固定种子通路。

## 14. 首版具体回放用例

### 14.1 修炼和恢复基准

F-01初态：天玄历387年一月，worldMonth=0，年龄252个月，炼气寿元上限1200个月，修为0/100，气血与灵力100，灵石100。有效资质10、真灵根、黄阶、普通环境、心境达标；所有额外倍率为1。固定本次基础奇遇检定不触发。

| 用例 | 操作 | 应断言的结果 |
|---|---|---|
| E2E-01 | 查看详情10次，空回车，改变窗口尺寸 | revision、worldMonth、随机状态及余额均不变 |
| E2E-02 | 提交一次修炼 | 修为19.5，worldMonth=1，年龄253月，余寿947月；年月为二月 |
| E2E-03 | 重发同一actionId | 返回duplicate；仍19.5，不再抽奇遇、不再扣月 |
| E2E-04 | 退出，模拟现实经过一夜，恢复 | 与E2E-02已提交机械状态完全相同；显示上次变化摘要 |
| E2E-05 | 在存储提交前／期间／之后分别强杀 | 重启只见原完整状态或新完整状态；无混合年龄、修为或随机游标 |
| E2E-06 | 写入磁盘满或权限失败 | 显示保存失败，阻止下一修炼；重试后最多结算一次 |

E2E-03～06各从明确快照独立运行，不能不说明前置状态就把结果串在一起。强杀测试仅针对专用测试目录和游戏测试进程，不能影响用户的工作任务。

## 15. 体验和性能验收方法

下列数值是首版候选目标，尚未测得。TASK-03记录一台参考Windows机器的系统、CPU、内存、存储、终端及构建版本；在TASK-17按相同条件复测。若未达标，定位或调整方案，不能把目标填成结果。

| 指标 | 采样方法 | 候选门槛 |
|---|---|---|
| 进程启动至可输入 | 新进程启动30次；报告首次启动、P50/P95；系统缓存状态注明 | P95≤2秒，无网络参与 |
| 普通行动机械结算 | 1000次合法动作，覆盖修炼／交易／月末事件；不含人工阅读 | P95≤50ms |
| 按键至已保存结果可见 | 真终端100次普通操作，包含落盘和渲染 | P95≤200ms |
| 正常退出 | 待输入节点退出30次，测到shell可输入 | P95≤500ms，存储故障单独统计 |
| 空闲CPU | 主屏静止5分钟，按整机总CPU百分比记录均值 | ≤1%，无持续刷新动画 |
| 空闲内存 | 主屏静置1分钟后记录工作集；长会话另查增长 | ≤100MB |
| 解压后发行体积 | 含实际运行依赖和M1内容，不含测试资源 | ≤80MB |
| 初次进入游戏 | 首次接触者使用预设，记录确认次数与用时 | ≤3次确认；不强迫配置完整属性 |
| 恢复后理解当前任务 | 人工试用，记录能否找到下一步和退出 | 无需翻历史日志即可继续 |

机械结算、存档耗时和终端渲染分开记录，避免将50ms规则计算目标误写成整个磁盘I/O一定50ms。首次启动不等同于严格清空系统缓存的冷启动；报告不得混用名称。

人工试玩覆盖30秒、2分钟、5分钟三档，以及中途接电话式突然离开。每档记录是否获得可说明的进展、一次选择读多少文字、是否知道已保存、回到工作花几步。少量试用仅用于发现问题，不宣称统计意义上的用户满意度。
